Detailed plan for phase 1 of [[dhcp-dns-rollout]] (DNS consolidation). Drafted Oct 31, 2026. Stages 2 to 5 and the 4b catch-all were run on Oct 31, 2026 (results in each stage below). 4b alerts and the soak are not done. It exists because the step-ca switchover ([[sop-stepca-cutover]]) needs working `.internal` names before ACME certs can be issued ([[stepca-acme-leaf-issuance]]).

## Scope
In: internal names under `homelab.internal` in Unbound, a forward chain from Unbound to Pi-hole that fails open with alerts, repointing every VLAN's hosts to its gateway's Unbound, firewall DNS rules.
Out, on purpose:
- Kea and all DHCP work (Daniel, Oct 31: not today).
- The OPNsense 26.7 hop (not the focus; only Kea waits on it).
- Retiring `homelab.local`, deleting its Pi-hole records, and renaming OPNsense's own system domain (`homelab.local`, seen in syslog on Oct 4). These wait until certs and NPM proxy hosts are moved to `.internal`. This is a change from the original phase 1 wording, which had Pi-hole record removal inside phase 1. Needs Daniel's confirmation.

Decided Oct 31, 2026: do the whole of phase 1, planned so connectivity is not lost. New ACME certs are issued under `.internal` names only.

## Design rules that keep connectivity
1. **The two zones never overlap.** `homelab.local` stays in Pi-hole untouched. `homelab.internal` is new and lives in Unbound only. Building the new zone cannot break anything because nothing uses it yet, and two resolvers never answer for the same name (the Sep 15 duplicate-answer bug).
2. **Add before remove.** Every new rule or resolver setting is added and tested while the old path still works. The old path is removed only after a soak.
3. **Canary first.** One host, then the VLAN. One VLAN at a time.
4. **Test with `dig` against the gateway before changing any host's resolver.** Lesson from [[incident-2026-03-30-soc-dns-firewall-gap]]: a VLAN with no DNS rule to the firewall fails silently.
5. **Every step has its rollback written down before it runs**, and a way in if the network path itself breaks.
6. OPNsense is on UFS, so there are no snapshots ([[session-2026-10-04-opnsense-25-7-11-patch]]). A downloaded config backup is the only rollback for OPNsense changes. Download one before each stage.

## Dependency to respect
Today `.local` names resolve only in Pi-hole. Unbound returned NXDOMAIN for them on Oct 4. So **no host may be repointed to Unbound before Stage 4a is verified**, or it loses every `.local` name. After Stage 4a, Unbound reaches `.local` through the forward to Pi-hole.

### Stage 4b decision (Daniel, Oct 31, 2026 11:39)
Daniel wants Pi-hole blocking on everything. The only exemption is the security lab, because a case was made for it earlier; no case was made for any other exemption. So: blocking everywhere except [[VLAN40]] (VLAN41 has no internet and no DNS by design). This overrides the earlier ambiguous reading of his "no" answer. Open technical question: Unbound's forwarding is per zone, not per client, so a catch-all forward to Pi-hole would apply to VLAN40 too. How to exempt one VLAN is not yet decided. Search findings (Oct 31, 2026 11:40, forum and mailing list sources, not Unbound documentation, so treat as likely rather than certain): Unbound views and tags only change local answers, not forwarding, and a July 2025 unbound-users post concluded that per-view forward-zones are not possible. The cache is shared across all clients, so a filtered answer cached for one VLAN can be served to another. The common advice is to give clients that need different filtering a different resolver. Options: (1) point VLAN40 hosts at a public resolver directly, needs a VLAN40 firewall rule and a DHCP option change, and changes the lab's restricted-outbound policy; (2) a second resolver instance only for VLAN40, not verified possible on OPNsense; (3) filter the lab too and allowlist what it needs in Pi-hole. The current VLAN40 DNS firewall rule is not recorded in the vault, so any choice needs it checked first.
