# step-ca issues leaf certificates through ACME

**Decided Oct 29, 2026.** Leaf certificates for homelab services will be issued by [[pve-int-stepca]] through an ACME provisioner, so services request and renew their own certs. This replaces the manual OpenSSL process on [[pve-ca-intermediate]].

## Context
All services deployed before step-ca existed still get their certs from [[pve-ca-intermediate]]: Elasticsearch/Kibana, Wazuh, Nginx Proxy Manager and all four Proxmox nodes. The step-ca instance uses the same intermediate key pair as that VM (confirmed Oct 29, 2026), so certs from either chain to the same root. See [[sop-stepca-cutover]].

## Naming (decided Oct 31, 2026)
New ACME certs are issued under `.internal` names only, so nothing is issued twice and later reissued. This depends on [[dns-phase1-consolidation]] being done first.

## Ruled out
- Manual per-service `step` commands with hand deployment. Less work than OpenSSL but no automatic renewal.

## Discussed, not decided here
- A public domain subdomain with a DNS-01 wildcard cert from a public CA for web UIs (the Reddit suggestion). Not part of this decision. step-ca would still be needed for SSH certs and the planned browser client certs either way.

## Open questions this raises
- ACME challenge type per service (HTTP-01 needs step-ca to reach each service on port 80 across firewalled VLANs; DNS-01 needs a DNS API).
- Proxmox and Elastic have no native ACME client path here, so each needs a renewal script or client.
- ~~Whether the ACME provisioner exists yet on step-ca.~~ Answered Oct 31, 2026 13:15 (`sudo pct exec 511 -- docker exec step-ca step ca provisioner list` from pve-services, container name `step-ca`): two provisioners, `Authentik` (OIDC, `enableSSHCA: true`) and `admin` (JWK). **No ACME provisioner exists yet.** It has to be added before any ACME client can request a cert. Whether the CA uses remote provisioner management (`enableAdmin`) or a static `ca.json` is not checked, which decides whether adding one needs a restart.
- NPM and custom ACME servers (checked Oct 31, 2026, not conclusive): one third-party page says NPM is certbot-based with no custom ACME URL in its UI, while NPM's own test repo ships a step-ca image with an ACME URL. Which applies to the installed version is not checked. Fallback is acme.sh or the `step` CLI plus a Custom certificate upload in NPM, with renewal handling unverified. NPM holds port 80 on services-host, so an HTTP-01 challenge there cannot use a standalone client.

## step-ca config facts (read Oct 31, 2026 13:18, `/home/step/config/ca.json` in container `step-ca` on LXC 511)
- `address` is `:9000`, so the ACME directory will be `https://stepca.homelab.internal:9000/acme/<provisioner name>/directory` once a provisioner exists.
- `enableAdmin` is true (remote provisioner management), so a provisioner can be added live with the admin credentials.
- `dnsNames` is `stepca.homelab.local` and `10.0.30.x`. **`stepca.homelab.internal` is missing.** ACME clients using the `.internal` name will fail TLS name checks until it is added to `dnsNames` and the container is restarted. Not changed yet.

- **NPM research, Oct 31, 2026 15:05 (searched NPM's GitHub issues and docs after the dropdown check):**
  - Native custom ACME server support has been requested many times in NPM's tracker (#301, #944 closed as not planned, #1417, #3518, #4820) and none of the results show it implemented. Confirms the dropdown.
  - Community precedent for exactly this setup: NPM issue #1884 (step-ca plus acme.sh plus a script that talks to NPM's REST API: log in at `/api/tokens`, validate and upload the cert via `/api/nginx/certificates/validate` and `/api/nginx/certificates/{id}/upload`, re-point proxy hosts). That post is old (about 4.7 years), so the script needs checking against the current API before use. A third-party API reference lists `POST /nginx/certificates/{id}/upload` and `/renew`.
  - NPM pull request #5959 hardens `POST /api/nginx/certificates/{id}/upload` so a custom cert already used by a proxy host is renewed in place under the same id. **Not checked whether it is merged or in the deployed `latest` image.** Without it, the #1884 approach is delete old cert, add new, re-point hosts.
  - **Empty-subject risk:** issue #1417 reports NPM failing to accept step-ca ACME certs with `Certificate is not valid (Cannot read properties of null (reading '1'))` because step-ca ACME certs have no subject by default; the fix reported there is forcing a CN in the ACME provisioner (`forceCN`, CLI flag `--force-cn`). The test cert from [[ubuntu-401]] has an empty subject. Not tested against NPM here.
  - Other proxies with native custom-ACME support per search results: Traefik (`caServer`, a 2023 blog shows it with step-ca), Caddy, GoDoxy, and linuxserver SWAG (a June 2026 change adds `CERTPROVIDER=custom`, merge status unverified). Not evaluated further.

- **Security record of NPM vs Caddy vs Traefik, searched Oct 31, 2026 15:40 (advisory databases and each project's GitHub advisories; counts are a rough guide only):**
  - **Nginx Proxy Manager:** authenticated RCE via the certbot plugin setup (CVE-2026-40519, versions 2.9.14 to 2.15.1, fixed after that, **affects the deployed 2.13.5**); auth bypass exposing TLS private keys for low-privilege users (CVE-2026-50892, 2.14.0); missing authentication on the certificate validate route (CVE-2026-93964, one third-party database labels it actively exploited with no fix, not verified); missing brute-force protection (CVE-2026-102334) and improper authorization on `advanced_config` (CVE-2026-102335), both listed through 2.16.0. It also inherits nginx and OpenResty core CVEs (three 9.2 CVSS nginx issues, NPM issue #5963 asking for a base image update, open about 9 days). Most NPM-specific ones need a logged-in user, so limiting who can reach the admin UI (port 81) is the main mitigation.
  - **Caddy:** about 23 CVEs listed for 2026, mostly in features a plain reverse proxy does not use (`file_server`, FastCGI, templates, Windows paths). Ones that touch a reverse proxy: `forward_auth` bugs (a FastCGI header normalization bypass in `copy_headers`, a wrong-upstream connection with `forward_auth` plus `reverse_proxy`), hop-by-hop headers leaking on WebSocket upgrades (CVE-2026-55458, low, fixed in 2.11.5, Oct 2026), and admin API authorization bypasses (config and PKI endpoints, moderate, May 2026). Caddy's admin API listens on localhost by default and can be turned off.
  - **Traefik:** many 2026 advisories. Many are Kubernetes provider issues (not relevant here), but core proxy ones include a TLS client auth bypass on HTTP/3, a path normalization auth bypass, a StripPrefix route auth bypass, a forwarded alias spoofing pre-auth bypass, and an HTTP request smuggling flaw through `Upgrade: h2c` that bypasses the middleware chain (CVE-2026-88008, Sep 2026, versions 3.4.2 to 3.6 are end of life, fix is 3.7.13).
  - **Takeaway:** none of the three is clean. The meaningful difference is that NPM is also a web application with users and a database, which Caddy and Traefik are not. The bigger risk in this lab is that the internal NPM image is 11 months old. Whatever proxy is chosen needs a routine update habit. `npm-dmz` (internet-facing via the Cloudflare tunnel) has not had its NPM version checked.
- **Zoraxy (NPM-style web UI proxy, Go) researched Oct 31, 2026 20:05:** 3 CVEs found. CVE-2024-52010 (Web SSH command injection, authenticated RCE as root by default, versions 2.6.1 to 3.1.2, fixed 3.1.3, container escape possible if the Docker socket is mounted as its docker README shows). CVE-2026-33529 (config import path traversal to RCE via a plugin, fixed 3.3.2, severity disputed: GitHub advisory and one aggregator say Low, another says 8.8). CVE-2026-108899 (basic auth bypass via path prefix in the Path Exception Matcher, up to 3.3.4, exploit published, fix in 3.3.5-rc1, a release candidate; whether a stable release has it is not checked). The maintainer's own release notes say the web file manager got too many security advisories (mostly post-login path traversal) and was replaced by a WebDAV server. Releases are authored by one maintainer. Same risk class as NPM (admin web app with RCE-after-login bugs), fewer CVEs but smaller project. **step-ca:** Zoraxy has a custom ACME server option, but issue #1290 (v3.3.4) says a private CA's directory fails TLS verification unless skipTLS is used, skipTLS does not persist on Preferred CA, and there is no UI to add trusted CAs. Workaround: one cert per file in `/usr/local/share/ca-certificates/`, `update-ca-certificates`, restart (Alpine skips combined PEMs). No report of Zoraxy with step-ca specifically was found.

## Decisions, Nov 9, 2026 (Daniel)
- Stay on NPM and use the workaround to get renewed certs into it. Caddy, Traefik and Zoraxy are not chosen. Revisit if the workaround proves fragile or NPM PR #5959 (in-place cert update) lands.
- Included in the cutover: a new intermediate key for step-ca with the CN corrected (no leading space), signed by the offline root, so VM 501's copy of the old intermediate key can be retired. Subject fields, validity and key type still to be agreed.
- Order agreed in chat: backups, then the new intermediate, then `forceCN` on the `acme` provisioner, then the NPM workaround.
